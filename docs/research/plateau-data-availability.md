# PLATEAU 取得可能データ整理（Cesium 非採用）

- 調査日: 2026-10-09（JST）
- 方針: キボミルでは Cesium を採用しない
- 対象: PLATEAU 配信サービスから現在取得できるデータと、非 Cesium 構成での扱い方

## 1. 結論

非 Cesium 構成で利用候補になるデータは、次の三群に分ける。

1. **そのまま利用できるデータ**
   - MVT: 道路、土地利用、都市計画決定情報、土砂災害警戒区域など
   - XYZ / TileJSON: 航空写真、背景地図
   - raster-dem: Mapbox Terrain-RGB、Terrarium
   - REST / GraphQL: データカタログと URL 検索
2. **取得後に自前変換して利用するデータ**
   - CityGML: 建築物、道路、土地利用、地形、災害、都市計画等
3. **取得可能だが現方針では使わないデータ**
   - 3D Tiles
   - Cesium quantized-mesh terrain

キボミルにとって特に重要なのは次の点である。

- **建築物は公式 MVT がない**。非 Cesium で建築物形状を使うには、CityGML を取得して GeoJSON、PostGIS、MVT / PMTiles、必要なら glTF / GLB 等へ自前変換する。
- **道路 `tran`、土地利用 `luse`、都市計画 `urf` は MVT がある**。表示用途では直接配信を試せる。
- 算定・選択・面積・接道判定は MVT の直接利用だけで決めず、CityGML または自前正規化データとの精度比較を行う。
- 航空写真と raster-dem は MapLibre 系で利用できる応答を確認した。ただし一部は説明ページとカタログの公開状況が一致しないため、試験配信として扱う。

## 3. 採用対象としないもの

### 3.1 3D Tiles

3D Tiles 自体はオープン標準であり、Cesium 以外の実装でも表示できる。しかし本検討では、クライアント互換性、メタデータ処理、スタイル、選択処理を含む 3D Tiles 系の評価を行わず、**利用対象外**とする。

公式カタログの配信件数集計には3D Tilesが含まれるため、件数を見るときは MVT と混同しない。

### 3.2 quantized-mesh terrain

`https://tile.plateauview.mlit.go.jp/terrain/layer.json` は Cesium 向け quantized-mesh である。MapLibre 等では raster-dem を使うため、本構成では対象外とする。

## 4. 変換なしで直接利用できるデータ

### 4.1 MVT

MVT は TileJSON 3.0 経由で取得でき、MapLibre GL JS 等から利用できる。URL の基本形は次のとおり。

```text
https://api.plateauview.mlit.go.jp/datacatalog/mvt/{cityCode}-{type}[-lodN][-interior]-{year|latest}/tilejson.json
```

例:

```text
https://api.plateauview.mlit.go.jp/datacatalog/mvt/13101-luse-latest/tilejson.json
```

調査日に上記の千代田区・土地利用 URL が TileJSON 3.0.0、タイルテンプレート 1 件、ベクターレイヤー 1 件を返すことを確認した。

#### 原典メッシュと MVT タイルの関係

PLATEAU の MVT は、原典 CityGML の地域メッシュに由来する地物集合を維持したまま、表示時には Web Mercator の XYZ タイルとして配信される。この二つは別の単位として扱う。

| 地物型 | 原典 CityGML の基本ファイル単位 | メッシュコード | およその一辺 |
| --- | --- | ---: | ---: |
| 道路 `tran` | 基準地域メッシュ（第3次地域区画） | 8桁 | 約1 km |
| 土地利用 `luse` | 統合地域メッシュ（第2次地域区画） | 6桁 | 約10 km |

MVT フィーチャーの `meshcode` 属性には入力 GML ファイル名の先頭要素が格納される。このため、道路は8桁、土地利用は6桁という原典ファイルへの所属を MVT 上でも追跡でき、同じ原典メッシュに属する地物集合として整理できる。変換時に自治体内の全地物を一つの新しい地域メッシュへ再編成するものではない。

一方、自治体単位の TileJSON は `scheme: xyz` と `{z}/{x}/{y}.mvt` のタイル URL を返す。各ズームでは、原典メッシュ由来の地物集合から対象 XYZ タイルと交差する形状が選ばれ、タイル外周のバッファを含む範囲へクリップ・量子化されて格納される。したがって、次の二層構造になる。

```text
原典由来の所属・地物集合
  道路     = 8桁地域メッシュ
  土地利用 = 6桁地域メッシュ
        ↓ 所属を meshcode として維持
MVT の取得・符号化単位
  Web Mercator XYZ = {z}/{x}/{y}.mvt
```

画面上では原典の6桁・8桁メッシュ単位のまとまりが残って見えるが、それ自体が一つの MVT タイルであることを意味しない。原典メッシュは地物の所属・集合を示し、XYZ タイルはズームごとの取得・描画範囲を示す。

根拠:

- [PLATEAU 3D都市モデル標準製品仕様書「ファイル単位」](https://www.mlit.go.jp/plateaudocument/toc7/toc7_02/toc7_02_01/_e4deae41-06c6-2fea-e6c3-29d4c79ff292/)
- [PLATEAU 可視化用データ変換仕様「共通属性」](https://docs.plateauview.mlit.go.jp/spec/visualization/#21-%E5%85%B1%E9%80%9A%E5%B1%9E%E6%80%A7)
- [PLATEAU 自治体単位の MVT TileJSON API](https://docs.plateauview.mlit.go.jp/api/rest/operations/datacatalogmvtspectilejsonjson/)

#### MVT の解像度

PLATEAU の MVT はベクトルデータなので、航空写真のような固定ピクセル解像度ではない。解像度は次の三つを分けて考える。

1. TileJSON のネイティブズーム範囲
2. 各ズームにおける地上タイル幅・画面表示縮尺
3. MVT 内部グリッドの `extent` による座標量子化

調査日に千代田区の土地利用・道路、札幌市の土地利用・道路・都市計画・土砂災害を確認した範囲では、TileJSON はすべて `minzoom: 10`、`maxzoom: 16` だった。ズーム17以上で表示しても、ズーム16のタイルを拡大表示するだけで、新しい詳細形状は配信されない。

東京付近（北緯約35.7度）での地上寸法は次のとおり。画面上の1ピクセル相当は、512ピクセルタイルとして算出した表示上の目安であり、元データの測量精度ではない。

| ズーム | 1タイルの地上幅 | 512px表示時の1px相当 |
| ---: | ---: | ---: |
| 10 | 約31.8 km | 約62.1 m |
| 11 | 約15.9 km | 約31.0 m |
| 12 | 約7.95 km | 約15.5 m |
| 13 | 約3.97 km | 約7.76 m |
| 14 | 約1.99 km | 約3.88 m |
| 15 | 約993 m | 約1.94 m |
| 16 | 約497 m | 約0.97 m |

ここでいう座標刻みは、タイル地上幅を `extent` で割ったMVT符号化上の理論値である。ズーム14以上では符号化グリッドが非常に細かいが、**元のCityGMLの測量精度がセンチメートル級になることを意味しない**。実際の精度は原典、作成方法、地物型、LOD、自治体ごとの品質に依存する。

低ズームでは座標が粗く量子化されるため、精密な境界確認、面積、接道、頂点比較には使用しない。ズーム14～16のMVTは表示、クリック選択、候補抽出、概算には利用でき、必要精度の検証に合格すれば算定利用も可能である。ただしMVT仕様上、タイル境界付近で地物がクリップ、重複、またはバッファ領域へ延長される場合があり、元形状をそのまま復元できる保証はない。確定計算に使う場合は、同一 `gml_id` の統合、タイル境界処理、座標変換、ジオメトリ修復を実装し、CityGML由来データと比較する。

キボミルでの暫定方針:

- MVT レイヤーはズーム14以上で表示開始する。
- ズーム10～13では軽量な概要データか別レイヤーを使い、PLATEAU MVTを直接読まない。
- 地物クリックと候補選択にはMVTの `gml_id` を利用できるか検証する。
- 面積・境界・接道判定にMVTを使う場合は、ズーム16、地物統合、重複排除、適切な平面直角座標系への変換を前提とし、許容誤差を実測する。
- 精度検証前は、MVTだけで確定値を出さず、PostGIS等の正規化済みデータを確定計算に使う。
- 対象自治体ごとにTileJSONの `minzoom` / `maxzoom` と代表タイル容量を事前測定する。

用途別の判断:

| 用途 | MVTの利用判断 | 条件 |
| --- | --- | --- |
| 地図表示・色分け | 利用できる | 通常の用途 |
| クリック選択・属性表示 | 利用できる | `gml_id`等で地物を識別する |
| 対象道路・土地利用の候補抽出 | 利用できる | 高ズームを使用する |
| 面積・境界の概算 | 条件付きで利用できる | ズーム16、座標変換、タイル境界処理が必要 |
| 接道候補の抽出 | 条件付きで利用できる | 距離許容値を設け、最終判定と分ける |
| 法規算定・課金・保存結果の確定値 | 検証前はMVT単独で確定しない | CityGML由来データとの誤差検証と再現性確保が必要 |

#### キボミルで優先確認する MVT

| 優先度 | コード | 用途 | 判断 |
| --- | --- | --- | --- |
| 高 | `tran` | 道路表示、敷地周辺の道路確認 | 現行道路データとの境界比較を行う |
| 高 | `luse` | 道路用地、公園用地、河川用地等の表示 | `org:LandUse` 相当属性がMVTに残るか確認する |

MVT はタイル境界での分割・クリッピングやズーム別表現を前提にした表示形式である。算定用の原典として採用する場合は、ポリゴンの完全性、座標精度、属性、重複、タイル境界の扱いを検証する。

```text
https://tile.plateauview.mlit.go.jp/mapbox/tilejson.json?format=png
https://tile.plateauview.mlit.go.jp/terrarium/tilejson.json?format=png
https://tile.plateauview.mlit.go.jp/tiles/plateau-terrainrgb/tilejson.json?format=png
```

ただし、地形の説明ページには MapLibre / Mapbox GL 向け `/terrarium/` と `/mapbox/` が「調整中・未リリース」と記載されている一方、実カタログには掲載され応答する。正式保証された本番配信とは見なさず、仕様・URL変更を許容した試験レイヤーとして扱う。

## 5. 自前変換を前提に取得できる CityGML

### 5.1 取得単位

CityGML は次の方法で取得できる。

- 自治体単位の全地物入り zip
- メッシュコードによる個別ファイル検索
- 空間 ID による個別ファイル検索
- 点または矩形の緯度経度範囲による検索
- 地名による検索
- 複数の個別ファイルをまとめる一時 zip

自治体単位 zip は 307 件あり、全体約 1,387.6 GB、中央値約 462.0 MB、最小約 15.2 MB、最大約 250.8 GBだった。大都市では自治体一括 zip を前提にせず、メッシュまたは矩形範囲で必要ファイルを取得する。

検索 API の基本形:

```text
GET https://api.plateauview.mlit.go.jp/datacatalog/citygml/{conditions}
```

条件例:

```text
m:533935                         # メッシュ
s:18/1/232853/103220            # 空間ID
r:139.7375,35.6583              # 点
r:139.7375,35.6583,139.74,35.66 # 矩形
g:千代田区                       # 地名
13101                            # 自治体コード
```

## 6. データ探索・更新に使えるAPI

Cesiumを使わなくても、配信APIはデータ探索と更新検知に利用できる。

| API | 用途 |
| --- | --- |
| RESTデータカタログ | 全データセット、最新データ、CityGML、配信URLの取得 |
| GraphQL | 地域・地物型等で必要フィールドだけ取得 |
| CityGMLファイル検索 | メッシュ、空間ID、矩形、地名、自治体で原典ファイルを検索 |
| CityGML属性API | `gml:id`から属性をJSON取得 |
| CityGML空間ID API | 空間ID内の地物ID・属性を取得 |
| Specification API | PLATEAU仕様書を検索・取得 |

推奨運用:

- 全件RESTレスポンスは2 MB以上あるため、クライアントで毎回取得しない。
- サーバーまたは定期バッチで取得し、必要な索引だけ内部配信する。
- `latest` は探索・表示用、固定年度は算定・再現用と分ける。
- ETag、取得日時、整備年度、元URL、変換バージョンを記録する。
- 公式APIは試験運用のため、外部レスポンスを内部DTOへ変換し、スキーマ変更を局所化する。

## 7. キボミル向け非 Cesium 構成案

```text
公式配信を直接利用
  MVT（道路・土地利用等） ─┐
  XYZ（航空写真・背景地図）├─> MapLibre GL JS
  raster-dem（標高）       ─┘

自前管理
  CityGML ─> 定期取得 ─> 検証・変換 ─> PostGIS ─> ASP.NET Core API
                              ├─> MVT / PMTiles ─> MapLibre GL JS
                              └─> GeoJSON ───────> 小範囲の編集・選択
```

この構成では、表示レイヤーの一部は公式配信を直接使える。一方、制限算定、敷地選択、道路境界判定など、結果の再現性が必要な処理は自前管理データを使う。

## 8. 現時点の採用優先度

| 候補 | 優先度 | 次の確認 |
| --- | --- | --- |
| `tran` MVT | 高 | 現行道路GeoJSONとの頂点・境界・属性比較 |
| `luse` MVT | 高 | 道路用地等の属性が保持されているか確認 |
| 建築物CityGML | 高 | 現行変換処理、ファイル単位取得、更新差分の整理 |
| CityGML検索API | 高 | 対象範囲だけを取得するバッチの試作 |
| オルソ `ortho-all` | 中 | 地理院タイルとの画質・年度・速度比較 |
| `urf` MVT | 中 | 全国都市計画GISとの差分確認 |
| raster-dem | 中～低 | ドキュメントとの不一致、URL安定性、標高精度を確認 |
| 3D Tiles | 対象外 | 評価しない |
| quantized-mesh | 対象外 | 評価しない |

## 9. 次の調査手順

対象自治体を一つ決め、以下を実施する。

1. `bldg`、`tran`、`luse`、`urf` の有無、年度、ファイルサイズをAPIから取得する。
2. `tran` と `luse` のMVTをMapLibreで表示する。
3. 同一範囲のCityGMLを矩形またはメッシュ指定で取得する。
4. 現行GeoJSON、MVT、CityGML由来データの境界と属性を比較する。
5. 建築物CityGMLから、現行用途に必要な2D外形、高さ、用途、IDだけを抽出できるか確認する。
6. PostGIS、MVT / PMTiles、GeoJSONの役割分担と更新単位を決める。
7. 公式配信停止時に、表示と算定がどこまで継続できるか確認する。
