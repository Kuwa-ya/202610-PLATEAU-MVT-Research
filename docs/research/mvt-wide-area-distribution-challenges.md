# PLATEAU MVT の広域・連続利用における課題

## 1. 目的

本書は、PLATEAU の自治体別 MVT を、自治体境界を意識させずに連続した地図として利用する際の課題を整理する。対象は主に土地利用 `luse` と道路 `tran` であり、現行ビューアで複数自治体を重ねて表示した結果を前提とする。

課題は次の3点に集約できる。

1. 自治体単位のデータ間で同じ地物が重複する。
2. 利用者が自治体コードを事前に指定する必要があり、地図移動に追従した広域表示が難しい。
3. 表示解像度を上げても、原典由来のデータ範囲・所属単位は地域メッシュのままであり、Web Mercator タイルと一致しない。

## 2. 前提となる配信構造

PLATEAU の MVT は、自治体コード、地物型、年度等を含むデータセット単位で TileJSON を取得する。

```text
/datacatalog/mvt/{自治体コード}-{地物型}-{年度}/tilejson.json
```

TileJSON が示す実際の取得 URL は Web Mercator の XYZ 形式であり、通信・描画上のタイルは `{z}/{x}/{y}.mvt` で取得される。一方、MVT 内の地物には、原典 CityGML のファイル単位に由来する地域メッシュへの所属が `meshcode` として残る。

したがって、次の2つの単位を分けて考える必要がある。

| 観点 | 単位 | 役割 |
| --- | --- | --- |
| データセットの選択 | 自治体コード＋地物型＋年度 | どの配信元を利用するかを決める |
| 通信・描画 | Web Mercator XYZ タイル | 表示範囲に応じて MVT を取得する |
| 原典由来の所属・管理 | 地域メッシュ | 地物がどの原典ファイル・範囲に属するかを示す |

XYZ 形式で取得できることと、データそのものが自治体や地域メッシュから独立して再編成されていることは同義ではない。

## 3. 課題1: 複数自治体による地物の重複

### 3.1 現象

現在の配信 URL は自治体コードを基点としている。隣接する複数自治体の MVT を同時に表示すると、自治体境界周辺を中心に、同一の `gml_id` を持つ地物、または同一・ほぼ同一形状の地物が複数のデータセットから取得される場合がある。

```text
自治体AのMVT ─┐
               ├─ 同じ道路・土地利用地物を含む可能性
自治体BのMVT ─┘
```

### 3.2 影響

- 同じ地物が重ね描きされ、色や透明度が意図より濃く見える。
- クリック時に複数の地物がヒットし、どのデータを正とするか判断が必要になる。
- 同じ地物の転送、デコード、描画が重複し、自治体数に応じて負荷が増える。
- 件数、面積、延長等を集計すると二重計上につながる。
- 年度や属性が自治体間で異なる場合、単純な `gml_id` の一致だけでは採用データを決められない。

### 3.3 現行ビューアの暫定対応と限界

現行ビューアは、表示中の地物について `gml_id` を優先し、IDがない場合は形状の署名を使って後から読み込んだ重複地物を非表示にしている。これは表示上の重なりを軽減する暫定処理であり、次の点は解決しない。

- 重複した MVT 自体の通信とデコードは発生する。
- タイル境界でクリップされた形状は、同一地物でも形状署名が一致しない場合がある。
- MapLibre が保持している表示範囲周辺の地物だけが判定対象となる。
- 年度、更新日時、完全性等に基づく優先順位を決めていない。
- 集計や後段処理で利用するデータの一意性は保証されない。

## 4. 課題2: 自治体コード指定による連続表示の制約

### 4.1 現象

表示前に利用者が5桁の自治体コードを指定し、自治体ごと・地物型ごとに TileJSON と MapLibre のソースを登録する必要がある。地図を隣接地域へ移動しても、移動先の自治体コードが登録されていなければ MVT は表示されない。

現行ビューアでは最大8自治体までを手動指定できるが、これは検証用の上限であり、広域を連続的に閲覧する仕組みではない。

### 4.2 影響

- 利用者は表示範囲に含まれる自治体コードを事前に把握しなければならない。
- パンやズームによって自治体境界を越えるたびに、対象コードの追加・削除が必要になる。
- 都道府県域や全国域では、ソース数とリクエスト数が自治体数に比例して増える。
- 自治体ごとのデータ有無、年度、地物型の差をクライアント側で扱う必要がある。
- 「現在の画面範囲に必要なデータだけを読む」という通常のタイル地図の操作感を実現しにくい。

### 4.3 必要となる仕組み

連続表示には、少なくとも次のいずれかが必要になる。

1. 表示範囲から交差する自治体を自動判定し、必要なソースを動的に追加・削除する。
2. サーバー側で自治体別 MVT を探索・統合・重複排除し、自治体コードを含まない単一の XYZ エンドポイントとして配信する。
3. 原典データを事前に正規化し、全国または地域ブロック単位の MVT / PMTiles として再生成する。

クライアント側の自動判定は既存配信をそのまま利用できる一方、重複通信やデータの一意性は解決しない。継続的な広域利用や集計を前提とする場合は、統合配信または事前正規化が必要になる。

## 5. 課題3: 地域メッシュと Web Mercator タイルの範囲不一致

### 5.1 現象

ズームを上げると MVT の座標量子化が細かくなり、表示上の形状解像度は向上する。しかし、原典データの所属・ファイル構成まで Web Mercator のタイル範囲へ置き換わるわけではない。

主な原典単位は次のとおりである。

| 地物型 | 原典の基本単位 | およその範囲 |
| --- | --- | --- |
| 道路 `tran` | 8桁地域メッシュ | 約1 km四方 |
| 土地利用 `luse` | 6桁地域メッシュ | 約10 km四方 |

XYZ タイルと地域メッシュは、投影法、境界位置、分割規則が異なる。このため、一つの地域メッシュは複数の XYZ タイルと交差し、一つの XYZ タイルも複数の地域メッシュにまたがり得る。

```text
原典の地域メッシュ ── 所属・地物集合を維持
        ↓ 交差判定、クリップ、量子化
Web Mercator XYZ ─── 通信・描画用のタイル
```

### 5.2 解像度と範囲を分けて考える必要性

高ズームで `extent` が大きくなることは、MVT 内部で表現できる座標の刻みが細かくなることを意味する。ただし、次の事項は改善されない。

- 原典の測量精度
- 原典ファイルが対象とする地域メッシュの範囲
- 自治体別データセット間の重複
- タイル境界での地物のクリップや分割
- 同一地物を複数タイルから復元・統合する処理

つまり、表示解像度の向上だけでは、広域配信の単位やデータ管理上の境界問題は解消しない。

### 5.3 影響

- XYZ タイルだけをキーにしても、原典データの所属や完全性を判断できない。
- タイル境界をまたぐ地物を集計・算定に使うには、`gml_id` 等による再統合が必要になる。
- 地域メッシュ、自治体境界、XYZ タイルの三種類の境界を同時に扱う必要がある。
- 土地利用のように原典単位が大きいデータでは、局所表示でも元のデータ集合が大きくなりやすい。
- キャッシュ、更新、差分管理の単位を XYZ のみで設計すると、原典更新との対応関係が追いにくい。

## 6. 課題間の関係

3つの課題は独立していない。

```text
自治体別の配信単位
    ├─ 複数自治体を重ねると重複する
    └─ 表示前に自治体コードの指定が必要

地域メッシュ由来の原典単位
    ├─ 自治体境界を越えて同じ地物集合が現れ得る
    └─ Web Mercator XYZ の境界と一致しない

結果
    └─ 自治体境界を意識しない、連続的で一意な広域MVTとして扱いにくい
```

画面上で重複を非表示にするだけでは、通信量、データ選択、集計の一意性、広域移動の問題は残る。

## 7. 目指す状態

広域利用に適した配信では、利用者が自治体コードを指定せず、表示範囲とズームだけで必要なデータを取得できることが望ましい。

```text
/mvt/{地物型}/{z}/{x}/{y}.mvt
```

この形を実現する統合レイヤーには、次の責務が必要となる。

- XYZ タイルと交差する原典・自治体データの探索
- `gml_id`、形状、年度、更新情報を用いた重複排除
- 採用する年度とデータの優先順位の固定
- タイル境界を考慮したクリップ、バッファ、ID維持
- ズーム別の簡略化と属性制御
- 原典の自治体コードと地域メッシュコードの来歴保持
- 更新単位、キャッシュ無効化、再生成範囲の管理

## 8. 今後決めるべき事項

| 論点 | 決める内容 |
| --- | --- |
| 一意性 | 同一 `gml_id`、同一形状、類似形状をどの条件で同一地物とみなすか |
| 優先順位 | 年度、自治体、更新日時、属性充足度のどれを優先するか |
| 配信方式 | 動的統合プロキシ、事前生成 MVT、PMTiles のどれを採用するか |
| 空間索引 | XYZ タイルから自治体・地域メッシュ・原典ファイルをどう検索するか |
| 更新 | 自治体別の更新を統合タイルへどう反映するか |
| 利用範囲 | 表示用途だけか、面積・延長・接道等の算定にも利用するか |
| 検証 | 自治体境界、地域メッシュ境界、XYZ タイル境界で何を比較するか |

## 9. 次の検証候補

1. 隣接する2自治体について、境界周辺の `gml_id`、`meshcode`、形状、年度を比較する。
2. 重複地物を「同一ID」「同一形状」「部分一致」「年度違い」に分類する。
3. 一つの表示範囲に必要な自治体数、MVTリクエスト数、転送量をズーム別に測定する。
4. 地域メッシュ境界と XYZ タイル境界をまたぐ地物について、分割と再統合の可否を確認する。
5. 統合プロキシと事前生成タイルの小規模な試作を行い、通信量、初期表示時間、更新容易性を比較する。
