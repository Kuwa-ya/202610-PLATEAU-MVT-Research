# PLATEAU MVT Research — 開発ゴール（2026年10月10日〜11日）

- 作成日：2026-10-10
- 対象：`plateau-mvt-research`
- 位置づけ：開発方針・到達目標の合意用ドラフト
- 前提：既存 README / docs に基づく現状整理。コード詳細および実機動作は未検証。

## 1. 最終ゴール

**Even G2 を主成果物とし、京都駅を起点に PLATEAU MVT と国土地理院の標高タイルを取得・共通処理し、現在位置と Even の向いている方角に連動した地理情報を Even G2 の画面で表示できる最小アプリを構築する。**

同時に、処理基盤を共有する 2DViewer を都市計画・土地利用の検証サイトとして整備する。3DViewer は地形投影・立体表示の実験サイトとして扱い、負荷や工数が大きい場合は機能縮小または中止する。

### 1.1 成果物と優先度

| 成果物 | 優先度 | 最終アウトプット |
| --- | --- | --- |
| Even G2 | 最優先 | GPS と Even の向きを取得し、MVT・標高タイルを解析して表示方向を追従させる。現在地の標高・用途地域・建ぺい率・容積率を表示し、ビルド後にプライベートアップロードしてクローズド実機試験 |
| 2DViewer | 高 | 土地利用を表示・選択し、属性と重なる用途地域（`USE_DISTRICT`）を取得・表示 |
| 3DViewer | 条件付き | 土地利用などを標高に沿うポリゴンとして表示し、可能なら建物を重ねる。過大な負荷・工数は避ける |

## 2. 共通方針

### 2.1 技術構成

- **Vanilla JavaScript + ES Modules** を基本とし、ビルド不要の静的 Web 構成を維持する（Even G2 のアプリパッケージングに必要なビルドは別扱い）。
- Even Hub SDK は実装時点の公式推奨かつ最新の安定版を採用する。実行モデル、表示 API、パッケージ形式なども公式の推奨構成を基本とし、理由のない独自構成や非推奨 API は採用しない。
- JavaScript・HTML から参照するライブラリ、スタイル、画像、フォントなどは、ライセンスと容量が許す限りパッケージ内へ配置する。CDN などの外部参照は、データ配信 API 等の不可避なものを除いて極力使用しない。
- データ取得、自治体索引、MVT デコード、属性解決、座標変換、幾何処理、標高取得・補間をできるだけ共通化する。
- UI・描画は各環境に合わせて分離する。MapLibre、Three.js、Even G2 表示 API の描画実装を無理に統一しない。
- Cesium / 3D Tiles は今回の共通表示基盤には採用しない。
- 既存機能を維持し、大規模な構造変更を避ける。

### 2.2 対象地域・座標系

- 既存の東京都データを維持し、**京都府全域**の市区町村区切りデータを追加する。
- 京都府の市区町村データは開発者側で別途変換・準備し、東京都と同様にリポジトリ内に配置する。
- 初期表示・初期原点は **京都駅**。
- ローカルな幾何演算の基準は **JGD2011 / 平面直角座標系第 VI 系（EPSG:6674）** とする。
- MVT・標高タイルの取得は Web Mercator の `z/x/y` を利用し、必要に応じて座標変換する。
- 取得データはすべて緯度経度を持つ前提とし、平面直角座標系と描画ローカル座標の対応は、地形描画に用いる「ちずうつし」の変換方法に合わせる。実データで原点・軸方向・単位の整合を確認する。
- MVT は zoom 16 を原本相当として扱い、表示開始ズームや非表示条件を設計する案を第一候補とする。ただし、本格開発を開始する前に、実データの形状・属性・量子化誤差・タイル境界を検証し、妥当性を確認してから確定する。この検証が終わるまで zoom 16 前提へ強く依存する実装は行わない。

### 2.3 データの取捨選択と属性解決

- **本フェーズ（2026-10 合意）:** codelist によるコード→日本語変換は **実装しない**。PLATEAU 2025 MVT のフラット属性（例: `urf_function`、`urf_buildingCoverageRate`）をそのまま表示する。京都・東京の実データで文字列が入ることを確認済み。
- 将来、コードのみの属性が必須になった場合に限り、限定 codelist の Attribute Resolver を再検討する（全 codelist 網羅はしない前提は変わらない）。

### 2.4 対象データ

| データ | 方針 |
| --- | --- |
| 土地利用 `luse` | 主対象。選択・属性表示・地形投影に利用。`uro_orgLandUse` が「道路」の地物を道路として扱うことを原則とし、実際の描画結果を確認しながら識別値と表示規則を検証する |
| 都市計画決定情報 `USE_DISTRICT` | 主対象。CityGML の `urf:UseDistrict` を内部識別子 `USE_DISTRICT` として扱い、実際の配信データセット名・MVT 属性構造を確認して取得する |
| 道路 `tran-lod1` | 今回の道路定義には使用しない。既存の取得機能をサブ機能として残す |
| 建物の 2D 情報 | `bldg_dm_geometric_attributes` を調査し、外形ポリゴンとして利用可能なら採用 |
| 建物の 3D 情報 | 既存「ちずうつし」の GeoJSON 取得・描画方式を参考に、静的サーバーから軽量取得できる範囲で追加 |
| 標高 | 国土地理院の標高タイルを利用。補間方式と座標対応は「ちずうつし」の方式に合わせる。zoom 16 を第一候補とし、欠損・解像度・境界整合と性能をベンチマークして設定を見直す |

### 2.5 用途地域の識別前提

| 項目 | 内容 |
| --- | --- |
| データ分類 | 都市計画決定情報 |
| CityGML フォルダ | `udx/urf/` |
| CityGML 地物型 | `urf:UseDistrict` |
| 内部識別子 | `USE_DISTRICT` |
| 用途地域の種類 | `urf:function` |
| 境界ポリゴン | `urf:lod1MultiSurface` |

上記を原典側の識別前提とする。MVT 上のレイヤ名、属性名、codelist 参照、建ぺい率・容積率の属性、欠損値、自治体・年度差は、実データで対応関係を確認してから実装へ反映する。

## 3. Even G2 — メイン成果物

### 3.1 必須の動作

1. Even G2 向けアプリとして起動する。
2. スマートフォンの GPS から現在地を取得する。
3. Even の方位情報を取得し、利用者が向いている方角に合わせて Viewer の表示方向を更新する。方位を取得できない場合は、真北を画面上として表示する。
4. GPS・方位・取得範囲・ズーム・通信状態・エラーなどのログを画面に表示し、動作を確認できるようにする。
5. 現在地から Web Mercator タイル座標を計算し、適切なズームと周辺取得範囲を決める。
6. 対象の土地利用・用途地域 MVT と国土地理院標高タイルを取得する。
7. 現在地を標高タイルおよび用途地域ポリゴンと照合し、標高、用途地域、建ぺい率、容積率を取得する。複数候補・境界上・欠損時の表示状態を区別する。
8. 処理済みデータと、土地利用データで「道路」と定義された部分を Even G2 画面に簡潔に表示する。
9. ビルド後、Even のプライベート配布経路にアップロードし、クローズドで実機試験する。

### 3.2 準必須目標

- 地形・土地利用を簡易 3D 表現で表示する。
- 「ちずうつし」の GeoJSON 取得を参照し、負荷が許容される場合に限って建物を追加する。
- グラスの画面サイズ、描画能力、通信量、更新頻度を考慮して表示情報を限定する。

### 3.3 設計上の留意点

- GPS・ネットワーク・MVT 処理はスマートフォン側を中心に設計し、グラス側は表示・入力に集中させる方向を基本とする。実際の実行環境・API 制約は SDK で確認する。
- 方位情報の取得元、座標軸、真北・磁北の扱い、更新頻度、平滑化方法を SDK と実機で確認する。位置更新と方位更新は分離し、頭部の向きへの追従でデータを毎回再取得しない。
- Three.js の 3D 表示をそのままグラスへ転用できるとは仮定しない。
- Even G2 の三次元表示は `even-g2-3d-summary` を参照し、スマートフォン側の Three.js / WebGL で描画した低解像度画像を Even Hub SDK で G2 へ送る方式を第一候補とする。SDK と実機で画像形式・転送性能・視認性を確認し、採用方式を確定してから本実装へ進む。性能を満たさない場合は Canvas 2D のワイヤーフレームまたは簡略図へ縮小する。
- 最初は位置・取得状態・簡略化した地理情報の表示を優先し、3D 表現は段階的に追加する。
- プライベート配布の要件、開発者権限、実機接続手順を早期に確認する。

## 4. 2DViewer — データ検証基盤

### 4.1 必須の動作

1. 京都駅周辺を初期表示し、土地利用 `luse` を表示する。
2. 土地利用ポリゴンをクリックして選択する。
3. 選択した土地利用の属性を取得し、MVT に含まれる名称・コードをそのまま表示する。
4. 選択ポリゴンに重なる都市計画決定情報（`urf:UseDistrict`、内部識別子 `USE_DISTRICT`）を取得する。
5. 重なる部分の幾何学的なクリッピングを行い、該当する用途地域を表示する。
6. 複数の用途地域にまたがる場合は、結果を複数表示できる構造にする。

### 4.2 条件付き目標

- `bldg_dm_geometric_attributes` の実データを確認し、2D 建物外形として利用可能な場合は描画する。
- 土地利用データの「道路」を共通の道路定義で描画し、他の土地利用との色・重なり・ラベルを整理する。`tran-lod1` は必要時に比較できる補助レイヤとしてのみ維持する。

### 4.3 精度上の扱い

MVT は配信用に量子化・分割されるため、クリッピングや面積などの結果はまず**表示・探索・検証用**とする。zoom 16 を原本相当として表示開始・非表示条件を組み立てるが、サンプルデータで形状精度、属性、境界の連続性を確認し、不十分なら前提を見直す。原典幾何との完全一致や法的・業務的な確定判定は今回の完了条件に含めない。

## 5. 3DViewer — 条件付き検証基盤

### 5.1 目標

- 3D の描画ライブラリ・描画 API・メッシュ生成方法を先に調査・比較し、性能と実装量を含む採用理由を設計書で確定してから実装する。
- 地表の画像を国土地理院タイルから **PLATEAU Ortho 2023** に変更する。
  - `https://tile.plateauview.mlit.go.jp/tiles/plateau-ortho-2023/{z}/{x}/{y}.png`
- 2DViewer と同等の土地利用選択・属性表示・用途地域表示を目指す。
- 土地利用ポリゴンと標高タイルのグリッドを組み合わせ、地形に沿った 3D ポリゴンへ変換する。基本路線は、ポリゴン頂点の標高サンプリングと標高グリッドに沿う分割・補間の併用とする。
- 「ちずうつし」の描画を参考に、建物データを別の静的サーバーから取得・描画するフローを検討する。

### 5.2 地形投影の設計方針

- 標高補間と緯度経度から描画ローカル座標への変換は「ちずうつし」の方式に合わせる。
- ポリゴン頂点で標高をサンプリングしたうえで、必要な箇所だけ標高グリッドに沿って分割・補間する。画面上の効果が乏しい細分化は行わない。
- 標高タイルは zoom 16 を第一候補とし、解像度、欠損値、タイル境界の整合、取得・生成・描画時間をベンチマークする。結果に応じてズーム、分割上限、更新範囲を見直す。
- ポリゴンの三角形分割、頂点数、キャッシュ、非同期取得。
- すべての入力を緯度経度へ対応付けられる前提で、平面直角座標系と描画ローカル座標の対応を「ちずうつし」の地形描画と一致させる。
- 頂点数、フレーム時間、メモリ、初期表示時間に上限を設ける。詳細計算により継続的な性能低下が生じる場合は地形追従メッシュを採用せず、2D ポリゴンを代表標高で浮かせる表現へ切り替える。

### 5.3 縮小・中止条件

Even G2 または 2DViewer の進捗を妨げる場合、またはベンチマークで許容性能を満たさない場合、複雑な地形投影・建物表示・UI 同等化を後回しにする。まず Ortho 画像差し替えと単純な地形投影を優先し、必要なら 2D ポリゴンを地表より少し浮かせる表現へ縮小する。

## 6. 共通処理層の責務案

| モジュール | 主な責務 | 主な利用先 |
| --- | --- | --- |
| Tile / Index | 現在地・表示範囲から `z/x/y` と自治体候補を解決 | 全3系統 |
| MVT Fetch / Decode | MVT の取得、デコード、必要レイヤ抽出 | 全3系統 |
| Attribute Resolver | ~~コード値と限定 codelist の照合~~ **本フェーズは未実装（MVT 直読み）** | — |
| Geometry / Overlay | 選択、重なり判定、クリッピング | 2D・3D、必要に応じ G2 |
| Coordinate Transform | 緯度経度・Web Mercator・平面直角 VI 系の相互変換 | 全3系統 |
| Elevation | 標高タイル取得、デコード、補間・サンプリング | G2・3D |
| Terrain Projection | 土地利用ポリゴンの地形投影・メッシュ化 | 主に3D、可能なら G2 |
| Viewer Adapter | 描画、入力、UI、表示最適化 | 各環境で個別 |

既存 `web/shared/mvt/` などの実装を優先して利用し、必要になるまで新規抽象化・ディレクトリ再編を行わない。

## 9. 開発運用ルール

- 開発量を増やさないことを優先する。
- 外部サイトの細かな巡回・参照や、ドキュメントの過剰な読み直しを避ける。
- 既存コードを不必要に繰り返し読み書きしない。
- 大規模なリファクタリングや無関係な修正をしない。
- バグが出た箇所に絞って確認・修正し、必要なテストだけ実施する。
- 不要な自動ループ、反復取得、大量のバックグラウンド処理を行わない。
- 外部配信の通信量・同時 fetch 数・キャッシュに配慮する。
- 実行時依存はパッケージ内配置を原則とし、JavaScript・HTML の外部参照を追加する場合は、必要性、オフライン時の挙動、ライセンスを確認する。
- 変更差分と進捗は Git で追う。

## 10. スコープ外・ドキュメント整理

- 既存ドキュメントから、今回の3成果物に無関係な別プロダクトの記述を削除する。
- 削除は README、設計、調査、統合文書など対象箇所を確認して行う。本ファイルの作成だけで既存ファイルが編集されたことにはならない。
- CityGML 原典精度の保証、法的な確定判定、全国本番運用、統合 PMTiles の事前生成は今回の必達対象外。

## 11. 実装前の確認事項と既定方針

| 項目 | 確認内容・既定方針 |
| --- | --- |
| Even G2 | 実装時点の公式推奨かつ最新の安定版 SDK を使用する。実行モデル、GPS アクセス、表示 API、パッケージ形式も公式推奨を基本とし、プライベート配布手順を実機試験前に確認する |
| Even G2 方位 | 方位センサー/API、真北・磁北、座標軸、更新頻度、平滑化を確認する。方位を取得できない場合は真北を画面上とする |
| Even G2 3D | `even-g2-3d-summary` のスマートフォン側描画・画像転送を第一候補とし、SDK と実機で転送性能・視認性を確認して確定する |
| MVT | 京都府の対象データ・年度・TileJSON・属性構造・codelist 参照先と、zoom 16 を原本相当とする扱いの妥当性を、本格開発の開始前に実データで検証する |
| 土地利用道路 | `uro_orgLandUse` が「道路」の地物を道路として扱うことを原則とし、各 Viewer の描画結果を見て識別値と共通表示規則を検証する |
| 用途地域 | 都市計画決定情報 `udx/urf/` の `urf:UseDistrict` を `USE_DISTRICT` として扱う。用途地域は `urf:function`、境界は `urf:lod1MultiSurface` を基準とし、MVT 属性、建ぺい率・容積率、境界クリッピングを実データで確認する |
| 建物 2D | `bldg_dm_geometric_attributes` に利用可能な建物外形が存在するか |
| 標高 | 「ちずうつし」の補間・座標変換方式、zoom 16 の解像度と性能、デコード方式、欠損値・タイル境界の扱い |
| Ortho | 配信範囲、利用条件、京都駅周辺の取得可否 |
| 3D | 描画方式の事前比較、地形投影の粒度、許容する描画負荷、2D 浮遊表示へ切り替える判定基準 |
