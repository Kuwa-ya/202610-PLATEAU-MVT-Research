# MVT 静的タイル索引と Three.js 統合（設計）

## 1. 目的

PLATEAU の自治体別 MVT（土地利用 `luse`、道路 `tran`）を、**ユーザーが自治体コードを入力せず**広域パンできるようにする。ランタイムでは配信データカタログ API を呼ばず、**ビルド時に生成した静的 JSON** だけを参照する。

表示・選択のベースは参照実装 [`docs/ref/kuwaya-geo/`](../ref/kuwaya-geo/)（ちずうつし）の 3D 地図と LOD とする。カメラが寄ったときだけ **TileJSON の `maxzoom`（実運用では多くが 16）** の MVT を取得・描画する。ズームアウト時は既存の地形・画像のみとし、MVT は**非読込・非表示**とする。

本設計は上記の **索引レイヤー** と **PoC 範囲（東京都＋埼玉県）** を定義する。実装は本書確認・コミット後に開始する。

## 3. スコープ

### 3.1 やること

- ビルド時にデータカタログから対象データセット一覧をスナップショット化する。
- **Web Mercator z12 親タイル単位**の JSON を配置し、その中に **z16 子タイル**ごとの関係市区コードを記述する。
- PoC 範囲では **z12 親ファイルを矩形内の全 154 件生成**する（データが無い親もファイルを置く）。
- ランタイムは視界に入った z12 親 JSON を読み、必要な z16 タイルに対し **1 市区コードだけ** MVT を取得する。
- kuwaya-geo のカメラ距離 LOD と連動し、MVT 表示は閾値以上のときのみ有効化する。

### 3.2 やらないこと（本フェーズ）

- CityGML / 自前 GeoJSON との精度突合（システム上不要）。
- 面積・接道・境界の算定用途向けの原典保証。
- ズーム 10〜13 の土地利用 MVT の読込（**非読込・非表示**）。
- 全国展開（PoC は東京都＋埼玉県。全国は同一スキーマで拡張可能）。
- 統合 PMTiles の事前生成（将来案。本フェーズは自治体別 MVT URL のまま）。

## 4. 配信・解像度の前提

- 各自治体・地物型の上限は **TileJSON の `maxzoom`** に従う。調査上は多くが `minzoom: 10`, `maxzoom: 16`（[調査記録](../research/plateau-data-availability.md)）。公式ドキュに「16 固定」の規定はないため、manifest には **ビルド時に読んだ `maxzoom`** を保持する。
- **取得・描画に使うズームは `maxzoom` のみ**（PoC では 16）。それより大きい地図ズームはタイルの拡大表示に相当し、新規詳細は来ない。
- MVT 取得 URL は TileJSON の `tiles[0]` テンプレート（`{z}/{x}/{y}.mvt`）を用い、**ビルド時に市区ごとの TileJSON を解決**し manifest にテンプレート URL を記録する（本番でカタログ API は呼ばない）。

## 5. 全体構成

```text
[ビルド（CI / 手元）]
  plateau-datasets 等 → スナップショット
  市区 bbox（境界データ）→ 交差計算
  → manifest（市区マスタ）
  → z12 親 × 154 JSON（索引・fetch 決定もここだけ）

[本番（静的ホスト）]
  kuwaya-geo 3D 地図
  LOD 閾値未満 → MVT オフ
  LOD 閾値以上 → 視界 z12 親 JSON 読込
              → z16 タイル列挙
              → fetch 市区 1 件決定
              → .mvt 取得・デコード → Three レイヤ

[PLATEAU CDN]
  .mvt / TileJSON 原典（取得のみ）
```

## 6. 静的ファイル配置

```text
data/
  snapshot/
    plateau-datasets-YYYYMMDD.json   # 再現用（任意だが推奨）
  manifest/
    luse-2025.json                   # 市区マスタ（東京都・埼玉県）
    tran-lod1-2025.json
  index/
    luse-2025/
      12/{x}/{y}.json                # z12 親ごと 1 ファイル
    tran-lod1-2025/
      12/{x}/{y}.json
```

- **分割単位は z12 の `{x}/{y}`**。都道府県コードでの索引ファイル分割は行わない（z12 タイルは県をまたぐため）。
- **fetch に使う情報は index と manifest のみ**。県境で複数市区が載る場合も、索引配列と最小コード規則だけで決める（別ファイルの優先ルールは置かない）。
- 都道府県は **manifest のフィルタ**（`prefCode` 等）と **PoC 矩形**で範囲を切る。

## 7. PoC 対象範囲（東京都＋埼玉県）

### 7.1 外接矩形（試験用・z12 154 枚の根拠）

ビルドは次の外接矩形に基づき、**z12 の全タイル ID を列挙**する。離島は矩形に含まれる分を含み、海は索引上 `[]` または空の `tiles` で表現する。

| 辺 | 緯度経度（おおよそ） |
| --- | --- |
| 北 | 36.22°N |
| 南 | 35.53°N |
| 西 | 138.73°E |
| 東 | 139.91°E |

この矩形での **z12 タイル数は 154 枚**（`x` 方向 11 × `y` 方向 14 前後の積で 154）。ビルドは **154 枚すべてに JSON ファイルを出力**する。中身が空でもファイル存在を保証し、運用・検証の抜けを防ぐ。

### 7.2 対象都県とデータセット

| 項目 | 値 |
| --- | --- |
| 都県 | 東京都（13）、埼玉県（11） |
| 土地利用 | `luse`、年度 `2025`（変更時は manifest の `year` を更新） |
| 道路 | `tran-lod1`、年度 `2025` |
| spec 例 | `13101-luse-2025`, `13101-tran-lod1-2025` |

manifest に含める市区は、スナップショット上 **当該都県かつ当該地物型の MVT 行が存在する市区**に限定する。

## 8. JSON スキーマ

### 8.1 `schemaVersion`

全 JSON で `schemaVersion: 1` を先頭に置く。将来の破壊的変更用。

### 8.2 市区マスタ `manifest/{dataset}.json`

```json
{
  "schemaVersion": 1,
  "dataset": "luse-2025",
  "featureType": "luse",
  "year": 2025,
  "maxzoom": 16,
  "minzoomCatalog": 10,
  "cities": [
    {
      "cityCode": "13101",
      "prefCode": "13",
      "name": "千代田区",
      "spec": "13101-luse-2025",
      "tilejsonUrl": "https://api.plateauview.mlit.go.jp/datacatalog/mvt/13101-luse-2025/tilejson.json",
      "mvtUrlTemplate": "https://…/{z}/{x}/{y}.mvt",
      "sourceLayer": "luse",
      "bbox": { "south": 35.65, "west": 139.73, "north": 35.70, "east": 139.78 }
    }
  ]
}
```

- `bbox` はビルド時に行政境界等から算出。タイル交差計算の入力。
- `mvtUrlTemplate` はビルド時に TileJSON を 1 回取得して埋める（本番はこの文字列のみ使用）。
- `sourceLayer` はデータセット依存（`luse` / `Road` 等）。TileJSON の `vector_layers` に合わせる。

### 8.3 z12 親索引 `index/{dataset}/12/{x}/{y}.json`

```json
{
  "schemaVersion": 1,
  "dataset": "luse-2025",
  "parent": "12/3626/1605",
  "tiles": {
    "36304/12840": ["13101", "13102"],
    "36304/12841": ["13101"],
    "36305/12840": []
  }
}
```

- **`parent`**: 常に `12/{x}/{y}`（ファイルパスと一致）。
- **`tiles` のキー**: **z16 の `{x}/{y}` のみ**（`16/` プレフィックスは付けない。親が z を担う）。
- **値**: 当該 z16 タイルと交差する市区コードの配列（5 桁文字列）。県境では 2 件以上あり得る。配列は **関係市区の記録**であり、実際に MVT を取る市区は fetch 規則（最小コード 1 件）だけで決める。

#### 空の表現（使い分け）

| 表現 | 意味 |
| --- | --- |
| z16 キー **なし** | ビルドで未評価、または PoC 初期のプレースホルダ親ファイル（`tiles: {}`） |
| **`[]`** | 評価済み。**この z16 に fetch 対象市区なし**（海、データ範囲外、MVT 未提供） |
| **非空配列** | 関係市区あり。fetch 規則で 1 件に決定 |

PoC の完成形では、各 z12 親の配下で **交差計算した z16 はすべてキーを載せ、該当なしは `[]`** とする。154 親のうち陸域外のみ `tiles: {}` のまま残る可能性はあるが、**ファイル自体は 154 件必須**。

### 8.4 fetch 規則

1. `tiles["x/y"]` が無い → その z16 はスキップ（索引未整備）。
2. `[]` → MVT 要求しない。
3. 非空 → **数値として最小の `cityCode` を 1 件選び fetch**する。

```text
fetchCode = min(codes by numeric cityCode)
```

県境で配列に複数市区が入っていても、**例外テーブルは持たない**。運用上問題が出た場合は、ビルド側で当該 z16 キーの配列を見直す（索引の再生成）か、将来スキーマを拡張する。

## 9. ビルド手順（設計）

1. **スナップショット取得**  
   `GET https://api.plateauview.mlit.go.jp/datacatalog/plateau-datasets`（gzip 可）を保存。

2. **manifest 生成**  
   pref 13・11、`format === MVT`、対象 `type` / 年度でフィルタ。各行の `composite_url` から TileJSON を取得し `mvtUrlTemplate`・`maxzoom`・`sourceLayer` を埋める。

3. **市区 bbox**  
   行政境界（国交省データ等）をビルド入力に取り込み、市区ごと `bbox` を計算。ソースと更新日を manifest のメタに記録する。

4. **z12 親 154 件の生成**  
   7.1 矩形で z12 の `(x,y)` を全列挙。  
   各親について:
   - ファイル `index/{dataset}/12/{x}/{y}.json` を **必ず作成**。
   - 初期テンプレ: `{ "schemaVersion": 1, "dataset": "…", "parent": "12/x/y", "tiles": {} }`。

5. **z16 交差の埋め込み**  
   各 z12 親の地理範囲内の z16 タイル（最大 256 件）について、全市区 bbox と交差判定。  
   - 交差市区リストを配列で記録。  
   - 0 件なら `[]`。  
   - PoC では親ごとに **計算した z16 キーをすべて `tiles` に載せる**（スパースだが親内は完全）。

6. **検証**  
   - 154 ファイル存在チェック。  
   - manifest の全市区で少なくとも 1 つの z16 タイルに出現するか（出現しない市区は警告）。  
   - 県境タイルで候補が 2 件以上の件数をレポート。

ビルドスクリプトの置き場所は実装フェーズで決める（例: `tools/build-mvt-index/`）。

## 10. ランタイム手順（kuwaya-geo 統合）

### 10.1 LOD 連動

- kuwaya-geo の `DISPLAY_LEVELS` / `settingForDistance`（[`lod.js`](../ref/kuwaya-geo/js/foundation/lod.js)）に **MVT 有効閾値**を定義する。
- 閾値未満: MVT レイヤを dispose し、**ネットワーク要求なし**。
- 閾値以上: 以下を実行。PLATEAU の実用上 **ズーム 14 未満では MVT を触らない**方針と整合させる（閾値は `detailLevel` / カメラ距離で 14 相当以上）。

### 10.2 タイル索引の読込

1. 視界 bbox（または既存のタイル選択ロジック）から **z12 親 ID 一覧**を得る。
2. `data/index/{dataset}/12/{x}/{y}.json` を fetch（キャッシュ可）。
3. 視界内の **z16 `{x}/{y}`** について `tiles` を参照。
4. fetch 規則で市区 1 件 → manifest から `mvtUrlTemplate` を解決 → z=16 で `.mvt` 取得。
5. Worker でデコードし、既存の local frame / feature レイヤパターンで Three に載せる。

### 10.3 重複・ピック

- 同一画面に複数市区が関与しても **fetch はタイルごとに 1 市区**。
- 地物 ID（`gml_id`）は MVT LAB と同様 `promoteId` 相当でハイライト・選択を検討する（実装詳細は別タスク）。

### 10.4 低ズーム時の選択・ダウンロード（要検証）

MVT は LOD 閾値未満では **非読込・非表示**とする。一方、kuwaya-geo 本体には **矩形選択やエクスポート（ダウンロード）** があり、MVT 未表示のスケールでも選択 UI は動き得る。

| 方針候補 | 内容 |
| --- | --- |
| **A. 不可（推奨候補）** | MVT 有効 LOD 未満では、MVT 関連の取得・出力を行わず、メッセージで寄るよう促す |
| **B. 条件付き** | 選択範囲を z16 タイル列にスナップし、オフスクリーンで索引＋fetch のみ実行（地形 LOD と独立） |

PoC では **A を基本**とし、実装着手前に kuwaya-geo の選択→エクスポートフローを追い、**「不可」とするカメラ距離／detailLevel の境界**を MVT 表示閾値と揃えるかどうかを確認する。境界が緩いと低ズーム選択で大量 z16 fetch になり得るため、**不可のスケールは MVT 表示開始と同じかそれより寄った側**に寄せるのが無難。

## 11. 実装フェーズのタスク分割（案）

| 順 | 内容 |
| --- | --- |
| 1 | ビルド: 154 z12 空ファイル＋矩形列挙ユーティリティ |
| 2 | ビルド: catalog → manifest（東京都・埼玉県） |
| 3 | ビルド: bbox 取込と z16 交差で `tiles` 埋め |
| 4 | ランタイム: z12 索引ローダー＋fetch 規則 |
| 5 | ランタイム: MVT デコード・Three レイヤ（kuwaya-geo 統合） |
| 6 | LOD 閾値・非表示時の dispose |
| 7 | kuwaya-geo: 低ズーム選択時の MVT／ダウンロード可否（§10.4） |

## 12. リスクと対応

| リスク | 対応 |
| --- | --- |
| カタログ・TileJSON の更新 | ビルドの再実行。`schemaVersion` とスナップショット日付で追跡 |
| 県境で最小コードのみ fetch | 索引配列に候補を残しビルドレポートで一覧。必要なら当該 z16 の配列を見直して再ビルド |
| z16 タイルサイズ（土地利用） | 視界タイル数上限・同時 fetch 数 cap・IndexedDB キャッシュ |
| 低ズームでの選択・DL | §10.4。まず不可方針で検証し、閾値を MVT 表示と揃える |
| kuwaya-geo ソースの利用条件 | 参照・統合方針はライセンスに従う。コピー範囲は実装時に確認 |
